# The course team's playbook

Rules the Assessment Agent has learned from reviews. The Course Architect
and the Assessment Architect follow every one; a broken rule is a finding. This copy is for the agents
that run in Claude Code on Paul's PC (`/course-team`). The server's agents
keep theirs in the database (Admin → Agents' work). When a review teaches a
new general lesson, add it at the end with the date and why.

How the rules learn (the feedback loop, see `node agents/track.mjs report`):
- A rule's number never changes; reviews cite it in each finding's `rule`.
  New rules go at the end and end with "(added YYYY-MM-DD)".
- A rule broken again after it was written isn't working. After one repeat,
  sharpen its wording with a worked example. After two, make it an automatic
  check in `agents/lib/checks.mjs` if a script can see it, and end the rule
  with "(checked by check.mjs)".
- Rules 1 to 8 were written on 2026-10-21.

1. The right answer must not be the longest option more often than chance would make it (about one question in four). Write wrong options of similar length and detail, each a real mistake learners make. *Why:* in the first Data Analytics draft the right answer was the longest in 45 of 55 questions.
2. Code, formula and query questions need wrong options that look just as complete as the right one: the same function with a wrong argument, a missing clause, a wrong default. *Why:* short, obviously broken code options give the answer away.
3. Overview hours must equal the module minutes plus the project and final test. A module with two hands-on tasks takes 60 to 120 minutes, not 40. *Why:* the first draft said 50 hours while its modules added up to 9.
4. Write the project rubric for the field: 4 or 5 criteria that say what good work looks like there, never the generic relevance/quality/presentation set. *Why:* a generic rubric lets every mentor grade differently.
5. State laws and regulations exactly: what they allow as well as what they forbid (India's DPDP Act, 2023 allows processing with consent or for certain legitimate uses). If unsure of a detail, say less rather than guess.
6. "Why the others are wrong" must say briefly why each wrong option is wrong, and must not start with "The others" (the page already labels it).
7. Every task that mentions a paid tool (Copilot, Power BI Pro, paid AI plans) must also be possible with a free one, and say so. *Why:* most MySkills students have no paid licences.
8. When software behaviour depends on the data or settings (for example how pandas reads 05/04/2026), say "can" or name the condition. Never state a default that is not always true.
9. On the day of review, re-check any regulatory or payment fact whose start date falls within the last 60 days or the next 90 on the regulator's own site (NPCI, RBI, a ministry). Until a start is confirmed, write "is due to start on" or "from a date NPCI will announce", never "began on". Check payment steps against current rules too: person-to-person UPI collect requests ended on 1 October 2025. *Why:* the Entrepreneurship draft said the UPI merchant fee "began on 15 October 2026" (NPCI had postponed it) and told learners to "request a payment" by UPI. (added 2026-10-26)
10. Every overview outcome must be shown by the learner's own work: a project deliverable, or a module task done on their own idea. If an outcome depends on circumstances (co-founders, a budget, existing customers), say so in the outcome and give a route for learners without them. *Why:* the Entrepreneurship overview promised "a written equity split with vesting" that a solo founder had no way to show. (added 2026-10-26)
11. Don't reuse a Practise task's scenario (same business, city and price) for a quiz question in the same module, even with the person renamed: quiz scenarios need a new context, so they test transfer, not memory. *Why:* m03-q1 copied t1's spoken-English class with Karthik renamed Karan. (added 2026-10-26)
12. After any fix that changes a person, business or number, re-read every sentence that refers to it in the same item (stem, options, explanation, why_wrong) and the sentence you edited: update pronouns and names, and split any sentence the fix pushed over 20 words. *Why:* in the Entrepreneurship round 2, the new seller Sunita was still "his", and two fixes made 28- and 32-word sentences. (added 2026-10-26)
13. Every final-assessment question names the skill it mainly tests (`skill`), and each skill a foundation-level module trains has at least 2 of them: the Foundation assessment places students skill by skill, and the database refuses to publish otherwise (checked by check.mjs). *Why:* AI-Powered Entrepreneurship passed every check, then the admin's Publish refused it: none of its 15 final questions named a skill. (added 2026-10-26)
14. Before writing a question or a task, name the Learn-card sentence it depends on: a question may test, and a task may use, only what a card has already shown (a function, a rule, a trap). *Why:* AI-Powered Data Analytics review 1 found five questions testing things no card taught (correlation vs cause, `$F$1`, NULL handling, pandas `&`, LAG), and review 2 found tasks needing `merge` and `drop_duplicates`, which no card showed. (added 2026-10-27)
15. Never refer to an option by its position ("the third option") in an explanation or why_wrong: name it by what it says. Options are shuffled, so positions change. *Why:* Data Analytics m02-q2 pointed at "the third option" when it meant the second. (added 2026-10-27)
16. Every tools task gives the learner data to work on: a free dataset they can open with a free tool, at a public address that returns the file itself (a CSV served as text/csv, with a CORS header for browser tools such as the DuckDB shell), and that address is live before the review. Check the content type, not just the status code. *Why:* none of Data Analytics' 20 tasks had data at first; then its Masala Mart links returned the website's HTML page with status 200, so the link check passed while no task could load. (added 2026-10-27)
17. Run every code option, right and wrong, in the tool learners will use (DuckDB, Google Sheets, pandas) before writing its explanation or why_wrong; SQLite is not a stand-in. A code line added to a Learn card must run on that card's own example data. *Why:* in Data Analytics, f08's why_wrong said LEAD lists months before a fall (it lists months before a rise), m05-q4 described SQLite's result where DuckDB stops with an error, and a merge line on m07 card 2 used a table its example didn't have. (added 2026-10-27)
18. Refer to other modules by number and title ("Module 7, Python and pandas for analysis"), never by internal id ("da-m07"): learners never see the ids. *Why:* four Data Analytics tasks said "da-m02", "da-m04" or "da-m07". (added 2026-10-27)
19. Before saving a question, cover the question and read only its four options. If one is the only careful, checking, hedging or professional-sounding choice, rewrite the others as named beginner mistakes made with the same care, until none stands out. *Why:* in Data Analytics a cheap model picked the right answer from the options alone in 50 of 55 questions after rule 1 was met: the tone of the options gave it away. (added 2026-10-22)
20. In a judgement question, write the fact that decides it into the scenario first, and make each wrong option what would be right under a different, plausible fact (another goal, data shape, audience, deadline or constraint). Test it: change that one fact and a different option should become right. The right answer must never be a wrong option plus one more good step (a re-check, a caveat); give the wrong option that step too. *Why:* with every wrong option a real mistake, a prober who knew the field still picked 46 of 55 from the options alone, because the right answer was the textbook practice whatever the case said. (added 2026-10-22)
21. When a wrong option is a sensible extra step (ask first, check whether the missing rows differ, pilot first), the scenario must state the fact that makes it pointless here. If the module's own Learn cards recommend that step, say in the scenario why it doesn't apply, or it is a second right answer. *Why:* m01-q1, f05 and m10-q1 each kept such a step, recommended by M1, M3 and M10's cards, and the clue tests chose it. A step that is only unnecessary is not wrong. (added 2026-10-22)
22. Every quiz question must be taught by its own module's Learn cards: be able to point to the sentence. If there isn't one, add it to a card (80 to 160 words) before keeping the question. *Why:* six Data Analytics questions tested what no card taught, and all 30 cards were under 80 words. (added 2026-10-22)
23. To judge whether something paid for itself, use profit (extra sales × margin, or cost saved) against a fair comparison, minus its cost. Never subtract the cost from extra revenue. *Why:* m10-q4's answer and M10 card 2 both did. (added 2026-10-22)
24. Every question has a title and a scenario; a bare code or recall question in the final becomes an applied case with numbers. *Why:* m03-q2, f06 and f07 had neither while the blueprint claimed they did. (added 2026-10-22)
25. In a module that teaches a tool (spreadsheets, SQL, Python, dashboards, AI assistants), at least one task must have the learner do the work in a free tool, on data given in the task (6 to 12 rows inline, or a CREATE/INSERT script), and hand in the result. Put the expected answer in the hint. "Describe", "plan" and "explain" tasks don't count as practice for the tool. *Why:* in Data Analytics seven of ten modules had only describe-or-plan tasks, so the learner never opened Sheets, a SQL playground or Colab, and 90 to 120 minutes promised work that wasn't there. (added 2026-10-23)
26. A Learn card introduces at most two new ideas, and shows a command or formula together with the result it gives on a few rows, not the code alone. *Why:* M5 card 3 (four window-function ideas) and M7 card 2 (six pandas commands) showed code but no output, though the quiz asked what the output would be. (added 2026-10-23)
27. After you change a task to run on a small table, run it as written (with the verification Python) and check that every filter, threshold and condition still has rows to act on, and that each filter has a row only it removes. Write the hint from the real output, not the reason you expect. *Why:* M4's `HAVING COUNT(*) >= 50` on six rows returned nothing, and M5's hint blamed the wrong filter for excluding a row. (added 2026-10-23)
